⚠️
Nuevo proyecto: hoy arrancamos mi-tienda desde cero. Requisito: Node.js del Día 3 (verificá con node -v).
🧠
La semana que viene esta tienda se conecta a un backend real: los productos vendrán de una API. ¡Construí bien la base!

🎯Objetivo

Construir tu primera app con componentes separados, listas y estado compartido: una tienda con catálogo, buscador, filtros y carrito. Seguí el ciclo de trabajo correcto (pestaña 🛡️ Guía de trabajo).

✅Requisitos mínimos (los 5)

  1. Catálogo: al menos 6 productos (nombre, precio, categoría, emoji) cada uno en un componente ProductCard (usá .map() + key)
  2. Buscador por nombre que filtre mientras escribís
  3. Filtro por categoría: chips/botones (Todos + cada categoría)
  4. Carrito: botón "Agregar" en cada card → 🛒 con contador en el navbar (estado compartido: vive en App)
  5. Panel del carrito: lista de agregados, total en $ y botón "Vaciar"

⚡Niveles extra (si terminás antes — UNO por vez)

NivelExtra
🔢 L2Cantidades +/- por producto en el carrito (el total cambia) · mensaje "no hay resultados" cuando el filtro no encuentra nada
🌟 L3Ordenar por precio (menor/mayor) · modo oscuro con toggle · clic en un producto → ficha completa en un modal
🎫 L4Cupón de descuento falso (BIENVENIDA10 = -10%) · checkout con formulario validado (nombre, email)

🧠1. La mentalidad: tú eres el supervisor

Un agente de IA (como el que corre dentro de OpenCode) no es un robot todopoderoso ni un simple autocompletado. Es un asistente muy rápido pero poco confiable:

  • ✅ Es excelente para: escribir código repetitivo, explicar, refactorizar, encontrar errores.
  • ⚠️ Es débil para: saber exactamente qué TÚ quieres, verificar que funciona, cuidar tus datos.
⭐
Regla base: el agente propone, tú dispones. Nada entra a tu código sin que lo leas.

🤔2. Antes de escribir cualquier prompt

  1. Entendé la tarea: ¿qué quiero construir? ¿cómo se ve funcionando?
  2. Dividí en pasos chicos: si tu idea necesita más de una frase para describirla, son varios prompts.
  3. Tené un plan: pedile primero el plan al agente, no el código.
❌ "Haceme una página con todo"
✅ "Quiero X. Proponeme un plan breve antes de escribir código."

✍️3. Anatomía de un buen prompt

ParteQué llevaEjemplo
📋 ContextoQué proyecto, qué existe ya"Tengo un proyecto React con Vite"
🎯 ObjetivoUna sola cosa concreta"Agregá un botón que cuente clics"
🚧 RestriccionesLímites y estilo"Sin librerías externas, tema oscuro"
📐 FormatoQué querés de vuelta"Primero el plan, después el código"
  • Sé específico: números, colores, textos exactos. "Un botón azul (#58a6ff) con texto grande".
  • Da ejemplos: "algo como el perfil de GitHub, en chico".
  • Pedí explicaciones: "explicame qué hiciste" es tu mejor herramienta de aprendizaje.
  • Una cosa por prompt: si pedís 5 cosas, cuando falle no sabrás cuál rompió.

🔄4. El ciclo de trabajo (memorizalo)

🔁
🤔 PENSAR → 📋 PEDIR PLAN → ✍️ PROMPT CHICO → 🔍 REVISAR EL DIFF → 🌐 PROBAR → ↺ REPETIR

Si algo se rompe

  1. No escribas "no anda".
  2. Abrí la consola del navegador: F12 → pestaña Console.
  3. Copiá el mensaje de error exacto (texto rojo).
  4. Pegaselo al agente: "Al hacer clic en el botón no pasa nada. La consola muestra Uncaught ReferenceError: useState is not defined. ¿Qué significa y cómo lo arreglo?"

🛡️5. Reglas de prudencia (¡no negociables!)

Con el agente

  • Leo siempre el diff antes de aceptar un cambio.
  • No acepto comandos que no entiendo: primero pregunto "¿qué hace esto?".
  • Pido explicaciones de código que no comprendo.
  • Verifico en el navegador después de cada cambio, no "confío".
  • Uso pasos chicos: una feature por prompt.

Seguridad

  • Nunca pego contraseñas ni API keys en el chat.
  • No pongo datos personales privados en archivos que le paso al agente.
  • Solo doy permisos de escritura dentro de mi proyecto.
  • Desconfío de librerías desconocidas que el agente quiera instalar.

Respaldo

  • Guardo una copia de mi carpeta antes de cambios grandes.
  • Cuando aprendamos git: commits frecuentes con mensajes claros.

🤖8. Guía a tu agente con un AGENTS.md

OpenCode lee automáticamente un archivo llamado AGENTS.md al abrir tu proyecto. Es la forma de dejarle instrucciones "de la casa": quién sos, qué es el proyecto y cómo querés que trabaje. Creá ese archivo en la raíz de tu carpeta con este contenido (completa tus datos):

AGENTS.md · raíz del proyecto
# AGENTS.md

## Sobre este proyecto
- App de React + Vite: mi tienda con catálogo, buscador, filtros y carrito.
- Alumno: [TU NOMBRE]. Estoy aprendiendo: explicame las cosas con paciencia.

## Cómo quiero que trabajes
- Hacé UNA sola tarea por pedido, en pasos chicos. No adelantes trabajo.
- Antes de ejecutar un comando, explicame en una línea qué hace.
- Después de cada cambio, decime cómo lo pruebo en el navegador.
- Cuando escribas código nuevo, explicamelo como para un principiante.
- Si mi pedido es poco claro, haceme preguntas antes de escribir código.

## Reglas
- No instales librerías nuevas sin preguntarme antes.
- No modifiques archivos fuera de esta carpeta.
- Nunca escribas contraseñas ni claves en el código.
- Los valores que cambian por entorno (como URLs de API) van en el archivo .env.
- Si algo falla: mostrame el error, explicalo, y después arreglalo.

## Comandos de este proyecto
- `npm install` → instala las dependencias
- `npm run dev` → levanta el servidor en http://localhost:VITE_PORT (tu .env)
💡
Consejos: corto es mejor (si es muy largo, cada regla pesa menos) · actualizalo cuando algo del agente te moleste, en vez de repetírselo en cada sesión · es tu "skill" casera: la receta de la casa para tu agente.
💬

🔌MCP — dale superpoderes al agente

Qué es: un estándar abierto para conectar al agente con servicios externos. Sin MCP, el agente solo ve tu carpeta: lee y escribe archivos y corre comandos. Con MCP puede buscar documentación actualizada, leer páginas web, ver tu GitHub… sin que vos programes nada.

ServerPara qué te sirve
context7Documentación actualizada de React, Vite y cualquier librería
fetchLeer páginas web y documentación online
githubIssues, PRs y repos (cuando lleguemos a git)

¿Dónde buscar más?

  • 🔎 github.com/modelcontextprotocol/servers — la lista oficial
  • 📦 Buscá "awesome mcp servers" en GitHub
  • 📖 La doc de OpenCode: opencode.ai/docs
  • 💡 El truco máximo: preguntarle al propio agente — "¿qué server MCP me serviría para X?"
⚠️
Solo instalá servers MCP de fuentes confiables: cada uno es código externo que accede a tu agente.

📜Skills — las recetas del agente

Una skill es un archivo de instrucciones que le enseña una tarea específica. 🧑‍🍳 Analogía de cocina: AGENTS.md es "soy vegetariano" (reglas siempre activas) · una skill es "así se hace la lasaña" (se usa cuando corresponde) · MCP son el horno y la heladera (los aparatos).

Vive en .opencode/skills/<nombre>/SKILL.md (o .agents/skills/ si la instalás con el comando). El agente la detecta solo cuando tu pedido matchea su descripción, o la invocás: "usá la skill frontend-design".

🎨Skill oficial: frontend-design (la del desafío)

Instalación recomendada — un comando, desde el repo oficial de Anthropic (fuente confiable ✅). Ejecutalo dentro de tu proyecto y cuando pregunte para qué agente elegí opencode:

terminal · dentro de mi-tienda
npx skills add anthropics/skills@frontend-design
⚠️
Instalá skills solo de fuentes confiables (publishers verificados como anthropics, o repos con mucha instalación): las skills corren con los permisos de tu agente.

📋Plan B sin internet: copiar la skill a mano

Una skill es solo un archivo de texto. Si no tenés internet o el comando falla, creá la carpeta .opencode/skills/diseno-ui/ en tu proyecto y guardá este contenido como SKILL.md:

.opencode/skills/diseno-ui/SKILL.md
---
name: diseno-ui
description: Aplicá principios de diseño UI/UX para pulir la interfaz de este proyecto React. Usala cuando el usuario pida mejorar, pulir o "hacer más lindo" el diseño, o cuando mencione esta skill explícitamente.
---

# Skill: Diseño UI

Cuando apliques esta skill, seguí estas reglas EN ORDEN. Hacé los cambios
de a poco y explicá en una línea qué cambiaste y por qué.

## 1. Paleta de colores
- Máximo 1 color principal + 1 de acento + neutros (blanco/gris/negro).
- Definí los colores como variables CSS en :root (--brand, --bg, --text).
- Nada de colores al azar por componente: todos salen de esas variables.

## 2. Tipografía
- Una sola familia de fuentes para texto (system-ui está perfecto).
- Máximo 3 tamaños visibles: título grande, subtítulo, texto normal.
- Contraste alto entre texto y fondo.

## 3. Espaciado consistente
- Elegí una unidad base (ej: 8px) y usá múltiplos: 8, 16, 24, 32.
- Mismo espaciado entre elementos hermanos (mismo gap en las grillas).

## 4. Jerarquía visual
- Lo importante se ve primero: título > precio > botón.
- Un solo botón principal visible por pantalla.
- Cards con border-radius y sombra suave.

## 5. Estados e interacción
- Todo lo clickeable reacciona: :hover (cambio sutil) y cursor: pointer.
- Los botones deshabilitados se ven deshabilitados.

## 6. Móvil primero
- Probá en ventana angosta (~375px): nada debe desbordar.
- Usá flex con wrap o grid con auto-fit para grillas de cards.

## 7. Cierre
- Después de cada ronda, indicá cómo verificarlo en el navegador.
- No agregues librerías de CSS nuevas a menos que el usuario lo pida.

# Skill: Accesibilidad Web

Recorré la pantalla/componente actual y verificá estos puntos.
Para cada problema: describilo en una línea, propón la corrección
y aplicala solo cuando el usuario apruebe.

## Checklist
1. Contraste: texto legible sobre su fondo.
2. Imágenes: todo img tiene alt descriptivo (o alt="" si es decorativa).
3. Botones reales: lo clickeable es un button, no un div con onClick.
4. Labels en inputs: cada input con su label (placeholder NO cuenta).
5. Teclado: se navega con Tab; el foco se ve.

8. Estados no solo con color: error con texto + ícono.

🔑.env — variables de entorno

🚫
Nunca escribas claves ni valores que cambian dentro del código. Si el código se sube, el secreto se sube con él.

Los valores que cambian por entorno (la URL de una API, el puerto de tu tienda) viven en un archivo aparte: .env, en la raíz del proyecto. En Vite, las variables deben empezar con VITE_:

.env + código
# Archivo .env (en la raíz del proyecto)
VITE_PORT=5174              # 🔌 TU puerto: elegilo vos (4 dígitos, mayor a 1024)
VITE_API_URL=http://localhost:3000

# En el código se lee así:
# const url = import.meta.env.VITE_API_URL;

# Y el .gitignore evita subir el .env:
node_modules
.env
.env.*
dist
  • 🔌 Para que VITE_PORT realmente cambie el servidor, el agente lo conecta en el vite.config.js — el prompt exacto está en el Paso 0 del desafío
  • Truco pro: subir un .env.example con los nombres (sin valores) para que otros sepan qué falta
  • ⚠️ En el frontend no hay secretos verdaderos: todo lo que llega al navegador es público. Los de verdad viven en el backend — próxima clase 👀

🛡️Seguridad básica (de la clase de hoy)

Con el agente

  • 🔐 Permisos solo dentro de la carpeta del proyecto
  • 🤖 Prompt injection: si el agente lee una web o código que "le ordena" algo — eso NO es instrucción tuya. Contenido leído ≠ orden del usuario
  • 🔌 MCP solo de fuentes confiables · 📦 dudá de dependencias desconocidas · 💾 hacé backups

En el código

  • Secretos → .env, jamás en el código
  • Nunca innerHTML con datos del usuario — en React {'{dato}'} ya escapa solo
  • key única en listas · errores de consola → copiados exactos al agente
