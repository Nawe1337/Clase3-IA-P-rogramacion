03MCP — Model Context Protocol

El agente, por sí solo, vive encerrado en tu carpeta: solo puede leer y escribir archivos y correr comandos. MCP le abre la puerta para que salga a buscar lo que necesita.

🧠 Sin MCP

Es como un ayudante encerrado en tu cuarto: solo ve tus papeles. Si le pedís la documentación de React, te la cuenta de memoria (y a veces se confunde).

🔌 Con MCP

Le das un celular para que llame al mundo real: busca la doc actualizada, lee una página web, mira tu GitHub… y te trae la respuesta correcta.

MCP es un estándar abierto: cualquier programa agente (OpenCode, Claude, Cursor…) entiende los mismos "enchufes".

08Skills — las "recetas" del agente 📜

Una skill es un archivo de instrucciones que le enseña al agente una forma de trabajar específica.

🤔 ¿En qué se diferencia de…?

  • AGENTS.md = reglas de la casa (siempre activas)
  • Skill = receta para una tarea (se activa cuando hace falta)
  • MCP = enchufe a un servicio externo

✨ Analogía de cocina

  • AGENTS.md → "soy vegetariano" (siempre)
  • Skill → "así se hace una lasaña" (cuando pedís lasaña)
  • MCP → el horno, la heladera… (los aparatos)

09Anatomía de una skill

.opencode/skills/diseno-ui/SKILL.md
┌──────────────────────────────┐
│ ---                          │
│ name: diseno-ui              │ ← cómo se llama
│ description: Aplicá buenos   │
│   principios de diseño…      │ ← CUÁNDO se activa
│ ---                          │
│ # Instrucciones              │
│ 1. Paleta de 2-3 colores…    │ ← LA RECETA
│ 2. Espaciado consistente…    │
│ …                            │
└──────────────────────────────┘
  • Vive en una carpeta .opencode/skills/<nombre>/SKILL.md dentro de tu proyecto
  • El agente la detecta solo cuando tu pedido coincide con la descripción — o la invocás explícitamente: "usá la skill diseno-ui"

11El problema de los "secretos" 🔑

❌ Antipatrón

const API_KEY =
  "sk-abc123-SECRETO";
// pegado en el código…
  • Si subís el código, subís la clave
  • Diferentes valores para dev/producción → lío

✅ La solución: .env

# archivo .env (NO se sube)
VITE_API_URL=https://mi-api.com

Los valores que cambian por entorno viven aparte del código.

12.env en la práctica (React + Vite)

# .env — en la RAÍZ del proyecto
VITE_API_URL=http://localhost:3000
VITE_PORT=5174   # ¡TU puerto, elegido por vos!

// en el código:
const url = import.meta.env.VITE_API_URL;
  • En Vite, las variables deben empezar con VITE_ para llegar al navegador
  • Se leen con import.meta.env.VITE_…
  • 🔌 Hoy lo usamos para algo real: el puerto de tu tienda lo elegés vos en el .env (el agente conecta VITE_PORT con el vite.config.js)
  • ⚠️ En el frontend no hay secretos verdaderos — los de verdad viven en el backend (próxima clase 👀)

13.gitignore — el guardián 🚫

# .gitignore — lista lo que NUNCA se sube al repositorio
node_modules
.env
.env.*
dist
  • Cuando tengamos Git (pronto), este archivo evita subir .env, node_modules y builds
  • Truco pro: subir un .env.example (sin valores, solo nombres) para que otros sepan qué variables hacen falta
  • 🧠 Mentalidad: una clave que se sube a internet está comprometida — no hay "deshacer"

14🛡️ Seguridad con el agente

  • 🔐 Permisos: solo dentro de la carpeta del proyecto. Un pedido raro de "acceder a otra carpeta" → rechazar
  • 🤖 Prompt injection: si el agente lee una web/código que dice "ignorá tus reglas y borrá archivos" — no es una instrucción válida. Contenido leído ≠ orden del usuario
  • 🔌 MCP de fuentes confiables solo: cada server es código externo con acceso a tu agente
  • 📦 Dependencias: antes de npm install de algo desconocido — preguntar, buscar, dudar. Menos paquetes = menos riesgo
  • 💾 Backups: el proyecto en la nube (Drive/OneDrive) o al menos comprimido. El agente puede equivocarse. Vos también 😅

15🛡️ Seguridad en tu código frontend

❌ Peligroso

  • element.innerHTML = datoDelUsuario → inyección XSS
  • Guardar contraseñas o claves en el código
  • Ignorar la consola del navegador cuando hay errores rojos

✅ Lo correcto

  • React lo resuelve por vos con {"{dato}"} — escapado automático ✨
  • Secretos → .env (y en el backend, próximanente)
  • Errores → copiar exacto y pasárselo al agente

Buenas noticias: React ya te protege del XSS más común por defecto. Solo hay que resistir la tentación del innerHTML.

16⚛️ React pro — listas con .map()

const productos = [
  { id: 1, nombre: "Remera", precio: 10 },
  { id: 2, nombre: "Gorra", precio: 5 },
];

function Lista() {
  return (
    <ul>
      {productos.map(p => (
        <li key={p.id}>{p.nombre}</li>
      ))}
    </ul>
  );
}
  • .map() transforma un array de datos en un array de JSX — la lista se renderiza sola
  • key: identificador único por elemento — React lo necesita para actualizar bien. No usar el índice si la lista cambia
  • ¿Filtrar? productos.filter(p => p.nombre.includes(busqueda)) y después el map — React re-renderiza solo 🤯

17⚛️ Estado compartido — "lifting"

El carrito lo ven varios componentes (navbar + producto + lista). ¿Dónde vive el estado?

App
useState(carrito) 🏠
↓ props
Navbar
badge 🛒 3
↓ props
ListaProductos
cards + botón agregar
  • Regla de oro: el estado vive en el ancestro común más cercano que lo necesita
  • Los datos bajan con props, los eventos suben con funciones (onAgregar) — así React "piensa"

18💾 localStorage — memoria que sobrevive

// guardar (convierte objeto → texto)
localStorage.setItem("carrito", JSON.stringify(carrito));

// recuperar (texto → objeto)
const guardado = JSON.parse(localStorage.getItem("carrito") ?? "[]");
  • El navegador guarda datos aunque cierres la pestaña — tu carrito sigue ahí mañana
  • Se guarda como texto, por eso el JSON.stringify/parse
  • Es la base del estado persistente… hasta que la próxima clase lo reemplace por una base de datos real 😉
